# Call & Answer: follow-up asks from the AI Analysis

Status: **design, not built**. Mockups in `index.html`, measured prompt runs in `PROTOTYPE.md`, the draft prompt in `prompt-draft.json` (installed nowhere), the build plan in `PLAN.md`. Nothing here changes product code.

## 1. What the owner asked for, and what this design takes it to mean

Owner, 2026-10-11, near verbatim: *"A real enhancement of the feedback-requesting piece. When the AI Analysis is done there are some questions that could be used for further discussion. The host could choose one and ask that specifically to the participants, and they get it on their phones/laptops. Or if there is a question — do others agree with statement X — or a multiple-choice ask. Perhaps the LLM could be asked to provide things like this along with its answer. Take a look at what we do in Build Room mode… Is this something we could do with a new AI Analysis prompt and system mechanism? We can mock up the ideas, build this with one Call & Answer question set and see what we get."*

What he said:
- After the read (What We Heard), the host can send one more question to the room's phones, laptops and tablets.
- Three kinds: an open question, agree or disagree with a statement from the room, and multiple choice.
- The model proposes them with the read; the host chooses.
- Learn from Build Room, where Claude's asks move the build forward.
- Prove it with one Call & Answer set.

What this design assumes (each is an open question in §11 if it could go the other way):
- It is part of the **feedback-requesting piece**: it sits where "Request feedback" sits today and takes that button's place, with the feedback round kept inside it.
- **The host always decides.** Nothing the model writes reaches the room without the host pressing Send, as in Build Room, where Claude proposes and the host approves.
- **One question at a time**, answered in under a minute, inside the round's results. It is not a new round and does not touch scores or the session's billing count.
- **Results go to the Stage and to the report.** Feeding them back into a new read is a second step.

Success: in a real session, a host sends at least one follow-up in most rounds without editing it heavily, the room answers it at about the rate it voted, and the report shows what the room thought about the line the read picked out.

## 2. What exists today (studied, with file:line)

**The read.** `lambda-functions/game/get-ai-summary.js` builds one prompt from the voice (`personas.js`), the context layer, the template (`sets/prompt-callandanswer-workie-advisor.json`), the output contract (`personas.js:457 buildOutputContract`: "Reply using exactly these N headings") and the angle, voice and host layers (`get-ai-summary.js:3415`). The C&A template's four sections are What the room said, What the room voted, **Discussion topics** and **Suggested next steps**. `parseAIResponse` (`get-ai-summary.js:355-461`) splits the reply at headings into `summaryText`, `discussionQuestions` (≤5) and `nextSteps` (≤5) by `SECTION_SYNONYMS` (`:349-353`), and keeps the whole reply as `markdownResponse`, which is what the Stage, the report and the PDF render. The read is generated by an async self-invoked worker (`:920-947`), stored on `QUESTION#nnn#AISummary` with a 30-day `ttl` (`:1860-1885`), then announced with `aiSummaryReady` (`:1939`). Haiku 4.5 is prefilled with the first heading; any model that refuses a prefill is asked for it in words and its preamble is cut by `ensureLeadingHeading` (`:3548-3572`).

**The model route.** `lambda-functions/game/claude-route.js` sends Haiku 4.5 and Sonnet 4.6 calls to Haiku 5.5 and Sonnet 5.5 on the Anthropic API when the platform switch is on. It drops temperature, turns a prefill into "Begin your reply with…" (`:188-200`), turns a **forced tool choice into `auto` plus "Answer by calling one of the tools"** (`:202-205`, `:230-233`), and treats a reply without the tool call as a failure that **falls back to Bedrock with the original request** (`:258-260`). So a tool call is a supported, checked output channel on both paths; a prefill-and-parse JSON reply is not needed.

**Where the read is shown.** Host and Stage are the same page (`GameHostPage.jsx`): RESULTS moves through three beats, `results`, `field-notes` (What We Heard) and `feedback` (`lambda-functions/game/stage-beats.js:42`, mirrored at `src/src/config/hostControls.js:84`; closed set, `tests/feedback-round-beat.js` holds the copies equal). On the last page of the read the dock's second button is **Request feedback** (`hostControls.js:809-834`); it builds the report and moves the beat to `feedback` (`GameHostPage.jsx`, `requestFeedbackRound`). The Host Remote reads the same decisions (`src/src/config/hostRemote.js`). Phones get `discussionQuestions` (`PlayerPage.jsx:1521`) but the read itself is a main-screen thing (relay pilot finding 12).

**The feedback round.** `lambda-functions/game/comments.js`: public routes, gated by the session STATE being `RESULTS#<that round>` and by membership: the claimed name must be a `PLAYER#` row in this game and, when that row carries a `ClientId`, the request must present the same one (`:330 writeComment`, header `:35-80`). Comments are keyed `COMMENT#nnn#anchorKind#ref#id` (`comment-keys.js:9-30`), sealed with `ENCRYPTED_FIELDS.comment` (`tenant-crypto.js:437`), and read whole by `create-report.js:170-183` into the round and session reports.

**Typed polls: the phone answer UI that already exists.** A poll round is "a survey question asked live" (`lambda-functions/game/poll-question.js:1-13`). The phone draws it with the survey inputs: `PlayerPage.jsx:3646` maps `{ choice: ChoiceInput, rating: RatingInput, yesno: YesNoInput, text: TextInput }`. `YesNoInput` already has an optional third answer, Not sure, and custom labels (`components/survey/YesNoInput.jsx:23-28`). The answer is stored as a structured `PollValue` next to its sentence (`websocket/message.js:608`), counted by the survey's own `aggregate` (`survey-aggregate.js:252`) through `pollTally` (`poll-round.js:51-56`), described to the model by `describePollTally` (`poll-round.js:66-`) and to the report by `pollAnswerText` (`poll-question.js:38-58`). Polls are always nameless (`anonymity.js`, NAMELESS_TYPES).

**Build Room's asks.** `lambda-functions/game/build-store.js`: three kinds, `suggest`, `choice`, `rating` (`:22`); one fixed rating scale, "1 needs work, 5 is great", that nobody can relabel so a 4 always means the same (`:23-29`); statuses `proposed → live → voting → results → decided | discarded` (`:30`); one open ask at a time (`words.js:64` "Finish the open question first"); `normalizeAsk` validates and caps every string the agent sends and writes errors the agent can read and correct (`:410`); options freeze once anyone has answered (`applyEdit`, `:448`). `build-room.js` does the I/O: rows sealed under the org, every row carrying the session's `ttl`, a revision bump and a `buildChanged` broadcast so every page refetches (`:1-140`). The words live in one place (`src/src/buildroom/words.js`): "Ask the room" (`:52`), "Show results" (`:30`), "Press Space to …" (`:109`).

## 3. Approaches considered

| | A. Fifth section of the read | **B. A separate asks call after the read** (recommended) | C. Host writes every ask; no model |
|---|---|---|---|
| What | The read prompt gains a heading "Follow-up asks" holding one json block; the parser strips it before storing `markdownResponse`. | A second, small call: the numbered answers (no names) and the stored read in, a `suggest_follow_up_asks` tool call out. | The drawer has only "Write your own". |
| Parsed (PROTOTYPE.md) | 4 of 4 | 4 of 4, tool called with `auto` every time | n/a |
| Time | Adds ~250-350 output tokens to a 12-15 s read | 5.3-6.5 s, off the read's path | 0 |
| Risk to the read | Changes a prompt tuned over months (games 1935, 4567, the relay pilot); a missed strip puts json on the projector, in the PDF and on phones; a reply cut at `max_tokens` loses the asks or half a fence | None: the read prompt and every renderer are untouched | None |
| 5.5 path | Plain text, works; but a fence inside a heading contract is a new parse | Tool call, already checked and fallen back from by `claude-route.js` | n/a |
| Grounding | Same faults as B | Same faults, but the call can be given only what it needs (numbered answers, no authors) | The host's own words |

B wins on everything except "one call", and the extra call is cheap and only made when wanted. C is kept inside B as "Write your own".

## 4. The mechanism

### 4.1 Generating suggestions

- **When.** After the worker stores a round's read and broadcasts `aiSummaryReady`, it makes the asks call in the same invocation, for Call & Answer rounds only, behind `FOLLOWUP_ASKS_ENABLED` (dev first, as `EVENTS_ENABLED` was). A Redo of the read invalidates the suggestions (they carry the read's `GeneratedAt`) and makes them again. A read that is the fallback template (`buildFallbackSummary`, `fallback: true`) gets **no** suggestions: the asks would be built on a read the model never wrote.
- **Input.** `prompt-draft.json → followUpAsks.instructions`, filled with the session title, the task (`resolveTask`, the same one the read uses), the question title, the two counts, **`{numberedAnswers}`** (new: every answer as `1. (14 vote points) "…"`, in the read's ranked order, never with a name), and the stored read. No author list is sent. The read itself may name a top-voted author (template rule 7), so the check below rejects names.
- **Call.** `claude-route.send(bedrock, cmd, { site: 'followup-asks' })`. Bedrock body: the instructions as the user turn, `tools: [suggest_follow_up_asks]`, `tool_choice: { type: 'tool', name }`, `max_tokens: 1200`, **no prefill**. On 4.x Bedrock this forces the tool; on the 5.5 route it becomes `auto` plus the route's sentence, and a reply without the call falls back to Bedrock. No temperature is set (5.5 rejects a non-default one, and none is needed).
- **Model.** Sonnet (4.6 on Bedrock, mapped to 5.5 by the switch), whatever wrote the read. Measured: Sonnet copied the room's words in 6 of 6 options against Haiku's 1 of 5, and grounding is the one property the check can only reject, not repair. Open question 12.
- **Why JSON through a tool, not a fenced block:** the 5.5 rules (no prefill, no forced tool choice) leave two ways to get structure: ask for a JSON reply and parse text, or ask for a tool call. The route already turns a forced tool into `auto` and **verifies the call happened**, with a Bedrock fallback when it did not; a JSON text reply has no such check and, without a prefill, nothing stops a preamble. 4 of 4 runs called the tool under `auto`.

### 4.2 The output, and the check

The tool's input schema is `prompt-draft.json → followUpAsks.tool.input_schema`:

```
{ asks: [                                    // 0 to 3
  { type: 'agree' | 'choice' | 'open',
    statement?: string,                      // agree: words copied from ONE answer, <= 20 words
    question?: string,                       // choice, open: <= 110 characters
    options?: [{ text: string, answer: int }],  // choice: 2-4, each from a different answer, <= 8 words
    answers: int[],                          // which numbered answers it comes from
    why: string } ] }                        // host only: what the answer would settle
```

The server never trusts it. `followup-grounding.js` (pure, new) checks every ask against the round's answers and the roster:

| Check | On failure |
|---|---|
| `type` known; `answers` in range; the fields its type needs are present | dropped |
| agree `statement` is words copied in order from one cited answer (case, punctuation and whitespace ignored), ≤ 20 words | **dropped**: a statement shown as the room's must be the room's |
| each choice option copied in order from its cited answer, ≤ 8 words, from different answers | kept, marked **Reworded** for the host (F2) |
| question ≤ 110 characters | kept, marked for the host; the editor shows the count |
| any roster name, first or last, in `statement`, `question` or an option | dropped |
| `why` | host-only; a name there is allowed but the prompt asks for none |

Measured against the prototype (`PROTOTYPE.md`): this check keeps 3 of 4 agree statements and drops the one Sonnet took from its own read; it marks every choice ask Reworded (0 of 4 copied exactly), which is honest; it passes 3 of 4 open questions and marks the fourth 5 characters long.

### 4.3 What the host does (mockups F1 to F5)

1. **F1.** On the last page of What We Heard, the dock's second button reads **Ask the room…** (with "3 ready" when suggestions exist) instead of Request feedback. Next round stays the primary. The Host Remote offers the same.
2. **F2.** It opens the host drawer (`min(560px, 100vw - 32px)`; on the Host Remote, a sheet). Up to three suggestions, each with its type, what the room would see, "For you: …" (the `why`), "From answers 1, 2 and 4", and a Reworded mark where the check set one. Below: **Write your own** and **Comments on the read** (today's feedback round, unchanged). Each suggestion has **Send as it is** and **Edit and send**.
3. **F3.** The editor: the type (agree, pick one, open), the words, up to four options. An option or statement that no longer matches an answer is labelled "Your words", never "Answer n". A live preview shows the phone card. **Send to the room** (amber), Cancel, Back and the X all go through one `requestClose()` that asks first when something was edited (engage-design hard rule 2).
4. **F4.** Sent: the Stage moves to a new beat `ask` and shows the question in Room type, the answers as the phones show them and the answered count. The dock: **Show results** (amber, Space) and **Cancel the question**.
5. **F5.** Show results closes the ask and freezes its tally; the Stage shows counts as bars (no percentages, as the reads rule). The dock: **Next round** (amber) and **Ask another…**, which reopens F2 with the used suggestion ticked. ← steps back to What We Heard, as from the feedback beat today.
6. **Next round with an ask still live** closes it first, with its tally, so no answer is lost.

### 4.4 What the room does (F6, F7)

The phone, laptop or tablet in RESULTS shows the live ask as a card with the existing survey inputs: **agree** is `YesNoInput` with `yesLabel: 'Agree'`, `noLabel: 'Disagree'`, `unsure: true` (Not sure); **pick one** is `ChoiceInput` with one pick and no write-in; **open** is `TextInput`, short (280). Send; the answer can be changed until results are shown; after Show results the card shows the same counts as the Stage, and which answer was theirs. No names, ever.

### 4.5 Where it sits in the round

**A fourth beat, `ask`, inside RESULTS**: `results → field-notes → ask → feedback` in the closed set. Not a new phase, because the round's STATE stays `RESULTS#nnn` (comments, reports, scoreboards and the remote all key on it) and the beat machinery already moves the Stage and the phones together. Not a Build Room-style side ask that can open at any time, because in C&A it only makes sense after the read and a mid-ASK interruption would cost a room its round. The beat is added to `stage-beats.js`, `hostControls.js STAGE_BEATS` and `PHASE_FOR_BEAT`, and to `hostRemote.js BEATS_PAST_THE_READ_BACK`, in one change, because an unknown beat silently reads as `results` everywhere (the `stage-beats.js` header explains the incident).

## 5. Data

All rows under `PK GAME#<id>`, sealed under the session's org like comments and Build Room rows (orgless sessions stay plaintext, as every row does).

| Row (SK) | What | Sealed fields | ttl |
|---|---|---|---|
| `FOLLOWUP#nnn#SUGGESTED` | The checked suggestions for this read: `Asks` (each with its check marks), `ForSummaryAt` (the read's `GeneratedAt`), `Model`, `CreatedAt`, `Dropped` (count only) | `Asks` | 30 days, as `QUESTION#nnn#AISummary` |
| `FOLLOWUP#nnn#ASK#<askId>` | One sent ask: `Kind` (agree, choice, open), `Statement` / `Question`, `Options` (each with `answer` or `ownWords`), `FromAnswers`, `Origin` (suggested, edited, host), `SuggestionIndex`, `Status` (live, closed, cancelled), `SentAt`, `ClosedAt`, `Tally` (frozen at close: `n`, counts per answer, and for open asks the texts in the aggregate's content-hash order) | `Statement`, `Question`, `Options`, `Tally` | `ROUND_RECORD_DAYS` (30), set with `if_not_exists`, as `ROUND#` rows are (`session-ttl.js:55-68`) |
| `FOLLOWUP#nnn#ASK#<askId>#A#<playerName>` | One person's answer: `Value` (the survey shape: `{v:'yes'|'no'|'unsure'}`, `[index]`, or text), `Text` (`pollAnswerText`), `PlayerName`, `At` | `Value`, `Text` | 7 days, as answer and vote rows |

One row per person per ask, overwritten on change, so a count is a count of people. The frozen `Tally` on the ask row is what the Stage's results, the report and the PDF read, so a report built after day 7 still has its numbers. A new entity `followup` joins `ENCRYPTED_FIELDS` in all three `tenant-crypto.js` copies (game, websocket, admin/shared).

**Anonymity.** Follow-up answers are **always nameless** on the Stage, on phones and in the report, whatever the round's own setting, as typed polls are. The name is on the answer row only to enforce one answer per person and membership. The host's Reveal authors does not apply to follow-ups. Open question 7.

**Billing.** Answers go through the new HTTP route, not `websocket/message.js`, so they never reach `session-count.js`: a follow-up is never a session's second answered question.

## 6. Routes

One function, `game/followups.js`, with a `{proxy+}` route family like Build Room's, because the stack is near its resource limit (about 440 of 500; memory, events work).

| Route | Who | Does |
|---|---|---|
| `GET /games/{id}/followups?round=nnn` | host (Cognito, `callerMayDriveSession`) | The suggestions (with `why` and marks) and every ask of the round with its tally |
| `POST /games/{id}/followups/suggest` | host | Make or remake the suggestions now (the worker normally has) |
| `POST /games/{id}/followups` | host | Send an ask `{kind, statement|question, options, fromAnswers, suggestionIndex?}`. Refused unless STATE is `RESULTS#nnn` and no ask of the session is live. Writes the ask, moves the round's beat to `ask`, broadcasts |
| `POST /games/{id}/followups/{askId}/close` | host | Freezes the tally (`aggregate`), sets `closed`, broadcasts |
| `POST /games/{id}/followups/{askId}/cancel` | host | Sets `cancelled`, beat back to `field-notes`, broadcasts |
| `GET /games/{id}/followups/live` | public | The live ask for phones: kind, words, options only. Never `why`, `FromAnswers`, suggestions or other asks. After close: the counts |
| `POST /games/{id}/followups/{askId}/answer` | public | `{playerName, clientId, value}`. Gated exactly as `comments.js writeComment`: STATE `RESULTS#<the ask's round>`, the ask `live`, a `PLAYER#` row for the name, and the `ClientId` when the row has one. The value checked against the kind with the survey's own validation |

Every write broadcasts `followUpChanged`; every page refetches (notify, then refresh, as everywhere).

## 7. Prompt changes

- **The read-back prompt does not change.** `sets/prompt-callandanswer-workie-advisor.json` keeps its four sections. Its Discussion topics still give the room something to talk about aloud; the asks are the sendable version.
- **One new prompt file**, `sets/prompt-callandanswer-followups.json`, from `prompt-draft.json → followUpAsks`, installed with `scripts/install-ai-prompt.js --apply` per tier like every set prompt (memory: set prompt files reach a tier only that way). It is not a Workie and is not chosen per session in the first build.
- **One new template variable**, `{numberedAnswers}`, built beside `responsesText` but with no names and with numbers the asks cite.
- **v2 (not in the first build):** a `{followUps}` line in the material of a Redo of the same round's read ("The room was then asked: … 11 agree, 3 not sure, 2 disagree"), built with `describePollTally`'s counts-only wording so the read's no-percentages rule holds.

## 8. Reports

`create-report.js` reads `FOLLOWUP#nnn#ASK#` rows beside the `COMMENT#` rows. `RoundReport.jsx` and `GameReport.jsx` gain a **Follow-up questions** section under each round's read (F8): the question, its type, its origin ("suggested by Workie from answer 6, sent as written"; "…edited by the host"; "written by the host"), the number who answered and the counts; open answers listed in full, nameless, in the tally's fixed order; a cancelled ask listed as cancelled with no counts. The saved PDF follows, since it renders the same report.

## 9. Reuse from Build Room, and what C&A needs differently

| Build Room has | C&A follow-ups |
|---|---|
| Claude proposes, the host approves before the room sees anything | **Same rule.** Workie suggests, the host sends. |
| One open ask at a time; "Finish the open question first" | **Same rule and words.** |
| One fixed rating scale nobody relabels | **Same idea:** one fixed agree scale, Agree / Not sure / Disagree, so an "agree" always means the same thing in the room and the report. |
| `normalizeAsk`: every string trimmed and capped, errors written for the sender to correct | **Same pattern** in `followup-kinds.js`, and a grounding check Build Room does not need (its asks are Claude's own words by design; C&A's claim to be the room's). |
| Options frozen once anyone has answered | **Same rule.** |
| Words in one module (`words.js`): "Ask the room", "Show results", "Press Space to …" | **Reuse the strings** in a C&A words module; do not import Build Room's file into the C&A page. |
| Phone answers drawn by `BuildPlayer.jsx` (`ChoiceAsk`, `RatingAsk`) | **Not reused.** C&A phones already import the survey inputs for typed polls; one phone UI per page. |
| `BUILD#` rows, the room's revision counter, the agent's MCP tools | **Not reused.** C&A asks live in the round, are made once from the read, and have no agent loop. |
| proposed → live → voting → results → decided | **Shorter:** suggested → live → closed (or cancelled). Nothing is "sent to Claude"; the report is the decision's home. |
| `suggest` (ideas, then a vote on them) | **Not in this design.** An open ask that then puts the room's answers to a vote is the natural second step after open asks ship. |

## 10. Risks

1. **The projector shows the drawer.** The host's laptop is usually the Stage, so the room can read the suggestions while the host chooses. They come from words the room has already seen, but an edit in progress is visible too. Mitigation: the Host Remote carries the same list (open question 1).
2. **The model's words pass as the room's.** 3 of the 12 v2 asks carried words that are in no answer (a statement and an option lifted from the model's own read, and three reworded options), and more of the v1 asks did. Mitigation: the grounding check drops an agree statement that is not the room's and marks reworded options; the editor labels edited lines "Your words"; the report says who wrote what.
3. **A read that invents a split makes asks that amplify it.** Haiku built a pick-one from its own read's framing. The read's split rule was fixed after the relay pilot; the asks rule A3 follows the read, so a bad read still leaks. Mitigation: Sonnet for the asks; the host's choice.
4. **Pick-one options are often not true alternatives** (2 of 4 v2 runs). Only the host's eye catches this. Mitigation: the editor; consider shipping agree first (open question 4).
5. **The dock's two-button rule.** Taking Request feedback's slot is the only way in without a third button; it moves the feedback round one click deeper.
6. **The 5.5 models were not measured.** The route's `auto` tool path was tested on 4.x only. A dev run must confirm Haiku 5.5 and Sonnet 5.5 call the tool and respect the limits before test.
7. **A closed set of beats.** Adding `ask` in one copy and not the other makes the button do nothing in front of a room with no error. Mitigation: the existing drift test, extended.
8. **Free text on the wall** (open asks). Same exposure as the comments wall today; ships second.
9. **Cost and time.** One extra call per round when enabled, about 6 s, in the worker after the read is out, so the host never waits on it unless they open the drawer within seconds of the read. About half a cent (Haiku) to a cent and a half (Sonnet) per round at list prices.
10. **Self-selection.** Those who answer a follow-up are not those who voted; the Stage and report say "16 answered", never "the room".

## 11. Open questions for the owner

1. **The suggestions are visible on the projector while the host chooses. Acceptable?** Recommended: yes. They are built from words already on the screen. Put the same list on the Host Remote for a host who wants to choose in private, and do not blank the Stage.
2. **"Ask the room…" takes Request feedback's place on the last page of the read, with Comments on the read inside it. Agreed?** Recommended: yes. It keeps the dock to two buttons and puts every way of asking the room in one place, which is what "an enhancement of the feedback-requesting piece" reads as.
3. **The agree scale: three answers or five?** Recommended: three (Agree, Not sure, Disagree), fixed, as Build Room fixed its rating scale. Five points invite an average and an average invites a percentage, which the reads forbid.
4. **Open questions in the first build?** Recommended: no; ship agree and pick-one first, open second. Open asks were the best-written suggestions in the prototype, but they put free text on the wall and need the comments wall's handling. If the owner wants one type only, ship **agree**: it was the most reliably grounded.
5. **Make suggestions as soon as the read is stored, or only when the host opens the drawer?** Recommended: as soon as the read is stored, in the same worker, when the feature is on. It costs about half a cent to a cent and a half per round and means the host never waits.
6. **What happens to a suggestion that fails the check?** Recommended: drop an agree statement that is not the room's words, and drop anything that names a person; keep a reworded option or an over-long question, marked for the host.
7. **Anonymity: always nameless, even in a round where names are shown?** Recommended: yes, as typed polls are. The round's names setting is about authorship of answers to the task; a follow-up is a quick poll.
8. **Should follow-up results feed the next read?** Recommended: not in the first build. They go to the Stage and the report. Second step: "Redo the read with the follow-up" on that round, using a counts-only `{followUps}` line.
9. **How many asks per round?** Recommended: no cap, one live at a time, at most three suggestions. "Ask another…" after results.
10. **Do phones see the results?** Recommended: yes, the same counts as the Stage, with their own answer marked. The relay pilot found participants see only their own result today.
11. **Billing.** Recommended: follow-up answers never count toward a session's second answered question. (They cannot, by construction, if the answers go through the new route.)
12. **Which model writes the asks?** Recommended: Sonnet (4.6, or 5.5 through the switch), whichever model wrote the read. It copied the room's words far more faithfully; it costs about a cent more per round.
13. **Write-in "Other" on pick-one?** Recommended: no. The options are the room's own; an Other box turns a one-tap question into a text one.
14. **Only Call & Answer?** Recommended: yes for now. Polls already are a one-question survey; trivia has no read to ask from. Revisit after a real C&A session.

## 12. The smallest version that proves value

Agree and pick-one only; one live at a time; suggestions made in the worker after the read; the drawer with Send as it is and Edit and send; the `ask` beat on the Stage with Show results; the phone card with the two existing inputs; the frozen tally in the round report. Dev only, behind `FOLLOWUP_ASKS_ENABLED`, measured in one real session with the agentic SDLC set before test. Not in it: open asks; choosing and editing on the Host Remote (the remote gets Show results, Cancel the question and Next round for a live ask, and the list in step two); a feed into a new read.
