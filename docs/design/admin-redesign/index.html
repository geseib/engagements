Engage2 admin console — redesign

Twenty-two runnable mockups plus an audit, for src/src/AdminPage.jsx and the five components it mounts. No build step, no CDN, no external asset — every file is self-contained.

Open the console → Run the audit

Serve this directory. python3 -m http.server 8123 --directory docs/design/admin-redesign
The audit reads inside iframes and cannot do that from file://. The mockups themselves open fine either way.

Every page carries its own design notes in a rail on the right. Press N or use the button at the bottom right to hide them — with them hidden the rail column collapses to zero and you are looking at the real console at its real width. That is the state to judge it in. The rail needs 1360px; below that it hides itself.
These carry worst-case content on purpose. A 98-character set title, 160 questions in the 24-category bitmask ceiling, a set that imported zero rows, a survey set that cannot be played at all, a session whose question set has been deleted, a session dated 1969, a user whose name is a UUID, a generation job that died at 41 of 100, and a prompt library with six broken records in it. The host redesign learned this the expensive way: copy chosen to fit produced sixteen green pages that hid nine defects.
Four things on these screens are defects in the product, drawn as they are. The Joined column on Users shows “—” for everybody, because the lambda returns created and the table reads createdAt. A poll CSV with Option1…Option5 imports with no options. A session dated 1969‑12‑31 is an epoch of zero formatted without a guard. A survey set can be created and can never be played. Drawing plausible values over any of them would have been the design hiding a bug.

The written work

INVENTORY.mdEvery element on the current admin surface, with a verdict. Read this first — it is what the design is a response to. RATIONALE.mdDecisions and derivations, what was rejected, and every place this disagrees with the host spec or with the brief. OPEN-QUESTIONS.mdEleven forks that could not be settled from the code. audit.htmlSix assertions × 22 mockups × 2 viewports. Each check was written after a defect it would have caught.

Mockups

Question sets — the centre of gravity

  1. The set list

    Home. A table, because someone scanning forty-one sets wants a table. Name, type, question count, one state column, one date.

    Worst case 26 rows under scroll; a 98-character title that must ellipsise; a Japanese title whose id is hash-derived; a set with 0 questions; a survey set marked Not playable; a legacy set with no engagement type stored.

  2. First run — no sets at all

    The highest-leverage empty state in the console, because every other screen is downstream of a question set. Three ranked ways in, not a shrug.

    Worst case the genuinely empty database — nav counts at zero too, which is the detail an empty state usually forgets.

  3. Filters matched nothing

    A different screen from 02, with different words and different exits. Names which filter is doing the excluding and what dropping each one would return.

    Worst case three filters stacked, including a three-word search, against a database with forty-one sets in it.

  4. Editing a set

    Its own screen with its own breadcrumb, not a form that appears below the list. Four panels, a pinned save bar that names the dirty fields, and the questions themselves — which the admin has never been able to see.

    Worst case the 98-character title in an h1; 24 categories; version 7 of 7 with v6 pinned by two live sessions; a question that was skipped on import; three past sessions in the delete panel.

  5. Replacing the questions from a CSV

    The “before you replace” beat, extended with the diff the current code does not compute: which categories are about to stop existing.

    Worst case a replacement that removes two categories and five questions while two sessions are pinned to an older version.

  6. CSV import with validation errors

    A validation report rendered before anything is sent, from the parse the browser already does. Three tiers: stops the import, would be skipped silently, known importer gaps.

    Worst case a 61-row file with a missing Title column, four different row-level failure modes including an unbalanced quote, the poll Option1..5 mismatch, and three image filenames with no file behind them.

  7. New set — the five ways in

    Replaces two duplicated engagement-type selects and five scattered buttons. Each path states what it is best for and what it costs you.

    Worst case the archive path, which loses the most, is on the same screen as the lossless one and has to say so.

The AI generation job — the state nobody had drawn

  1. Setting up a generation

    The trivia builder’s configuration, with the pass count and time estimate derived from the worker’s real token budget.

    Worst case 100 questions × 6 choices × 24 categories — the maximum the API accepts, which is six sequential model calls.

  2. A job in progress

    The centre of this redesign. The work is server-side, so it gets a home outside the modal that started it: a live count, the questions landing as they are written, a jobs tray in the top bar, and “Close — this keeps running” as the primary action.

    Worst case two jobs at once, one of them still queued; a third finished and waiting for review; and the honest statement that the job cannot be cancelled, because no cancel endpoint exists.

  3. A job that failed

    Partial failure named as partial failure. Today a job that dies with items already written renders the review screen and the error is shown nowhere — failure looks exactly like success.

    Worst case 41 of 100, a rate-limit error with no code and no retryable flag, two warnings that are returned today and displayed nowhere, and sixteen items dropped server-side as near-duplicates without any client-visible signal.

  4. Reviewing what came back

    A table, not a one-at-a-time carousel, with per-item reject — which does not exist today, so one bad question means importing it or discarding eighty-three good ones.

    Worst case you asked for 100 and got 84, one of which has no mappable correct answer.

Sessions — the tab that had no list

  1. The session list

    “Game Management” today is a free-text box for a game id and a Delete All button. GET /games has been deployed all along.

    Worst case a live session mid-round; a session whose question set was deleted so no report can ever be built; a session dated 1969; a 187-player session.

  2. No sessions yet

    An empty state that answers the question behind the question — a host can only start a session from an active set, and this console knows how many are not.

    Worst case the state where the console looks broken but isn’t.

Destructive actions

  1. Deleting a question set

    Consequence, not danger. Names the three sessions that used the set and says, per session, what deleting it decides — because a report is built from the live set when it is first requested.

    Worst case one session already has a saved report, one is live right now, and one can never produce a report again. Needs one backend change, stated on the screen.

  2. Deleting every session

    Counts before it asks. Type-to-confirm, and the environment repeated in the footer of the dialog.

    Worst case a live session with 38 players, six saved reports and ~2,400 answers, all going at once.

Users, prompts, archive, settings

  1. The approval queue

    A queue at the top of the screen with a named verb, plus a count in the nav visible from every other page. Today it is the second of four filter tabs.

    Worst case a 35-character double-barrelled name on a 70-character email; a person whose name is a UUID; an unconfirmed address; and someone who has been waiting 21 days.

  2. Nobody waiting

    The queue keeps its frame when it is empty. A section that disappears is a section you stop looking for, which is the one thing an approval queue must not be.

    Worst case there is no honest “no users” state — an admin is reading the screen — so this is the real steady state instead.

  3. The prompt library

    One list where there are three today. Generators and summaries are the same record with different shapes; the archive’s export tab renders a third variant of the same card.

    Worst case 47 prompts of which six are broken in four different ways, including one with no id and one imported without its body.

  4. Editing a prompt

    Instructions, output format, and the variable palette. Saving writes a new version rather than overwriting the old one — the versioning code exists and the editor simply never asks for it.

    Worst case a Wavelength prompt, whose six variables are unreachable in the current UI because the palette’s group ordering is a literal array that omits Wavelength.

  5. The cross-environment archive

    One shared store behind one public URL. Source environment is the first column, because this is a promotion tool.

    Worst case an item exported from an environment that resolved to unknown; a trivia set whose tags and images have no column in the archive CSV; an art set whose image files do not travel at all.

  6. The archive is unreachable

    Today a failed archive load renders as “No archive items found” — an outage indistinguishable from an empty archive.

    Worst case a silent timeout with no status code, and a local workaround offered instead.

  7. Settings

    Where you are, what you are pointed at, and two diagnostics described by who sees the result rather than by what they enable.

    Worst case the archive row, which has to admit that dev, test and prod share one store.

Colours are the Warm Summit tokens from docs/handoff/warm-summit-design-spec.md, unchanged, plus one new text-only tint (--danger-text) derived in RATIONALE.md §5 for the same reason the host spec added --success-text. Type sizes are not the host spec's ladders — those are derived for a projected image read at 25 feet, and this is a laptop at 24 inches. The derivation is in §3.

The mockups are generated from _src/ so the shell stays identical across all twenty-two: python3 _src/build.py. The generated files are the deliverable; _src/ is kept so a change to the shell does not have to be made twenty-two times. Display type falls back to the nearest system face — production self-hosts Archivo Expanded, which is wider.
