Engage2 player screen — redesign mockups

Open the deck viewer →

Steps through all 23 in a device frame with ← →, and switches device with 1 phone 375×812, 2 tablet 768×1024, 3 laptop 1280×800. The three type ladders are real media queries, so the device switch is the only way to see them fire. Serve this directory — python3 -m http.server 8124 --directory docs/design/player-redesign.

This surface had never been designed. There is no player-facing design document anywhere in the repository and the host spec does not mention the player's screen once. Read INVENTORY.md first — it is the honest accounting of what src/src/PlayerPage.jsx renders today, including four states that cannot render at all and one that renders a blank page. Then RATIONALE.md for the derivations, the arguments and the places this design disagrees with the host spec and with the brief, and OPEN-QUESTIONS.md for the ten decisions that are not mine to make. audit.html is the verification: ten assertions × 23 mockups × 3 device profiles, 690 in all, and one of them changed the design.
The organising idea is volume. Every state is ACT, REST or WATCH. ACT — the phone is the only place the task can be done: full contrast, amber primary, a dock. REST — the task is done: no dock at all, no amber, nothing to press. WATCH — the shared screen is the show: the phone carries only what is personal and therefore cannot be on the stage. The state machine sets the volume; the player never chooses it.

The 23 states

  1. 01Joining — code and name

    The first thing every participant ever sees. Two fields, one button, no account, no app. The name field carries the only honest place to say what a name is for.

    Worst case carried: A 34-character display name; the code typed by hand rather than arriving in the URL.

  2. 02Joining — the code is wrong

    The single most common failure, and today it is an alert() that says nothing useful. The error is inline, attached to the field that caused it, keeps what was typed, and says where to look for the right value.

    Worst case carried: Amber, not red: red is reserved for destructive. A four-digit code is easy to mistype and easy to misread off a projector, so the message names both causes.

  3. 03Joining — the session has finished

    A distinct outcome from a wrong code, and a dead end rather than a retry loop. Today this is the same generic alert as a typo, so a late arrival keeps retyping a code that will never work.

    Worst case carried: No form is rendered at all. The only action offered is the one that can succeed.

  4. 04Joining — a private session

    The access-code branch. Today it appears as a second screen after a failed join, having thrown the name away; here it is one screen with three fields and nothing lost.

    Worst case carried: Long instruction copy, and the access code shown as free text because it is not a secret worth masking — it is read aloud in the room.

  5. 05In, and waiting for round 1

    The first REST screen. The phone has nothing to do, so it offers nothing to do — no dock, no amber, no pulse animation, no player count. It spends the idle minute on the one piece of housekeeping that is worthless later and priceless mid-session: how to get back in.

    Worst case carried: The longest plausible display name, and an event title long enough to force the rail ellipsis.

  6. 06ASK — trivia

    Pick one of A–F. The whole answering affordance is above the dock and reachable without leaving the question on screen. Selection and the button it enables share one amber thread.

    Worst case carried: Six options, not four — the code renders A–F. Option F is 121 characters, which is the longest option in the shipped question sets.

  7. 07ASK — call & answer

    Free text. The question stays on screen while you type — today a full-screen textarea overlay covers it, so people answer from memory. The dock holds one submit, not three.

    Worst case carried: The longest plausible prompt (247 characters) plus a per-set custom instruction, on the narrowest phone. The composer is deliberately not tall: the question must stay visible above the keyboard.

  8. 08ASK — composing, keyboard up

    The state that decides whether the previous screen works. A 247-character prompt is nine lines at the primary rung; with a soft keyboard up there is roughly 430px of usable height, and the question and the composer cannot both have it. So on focus the question condenses to three lines at body size and pins itself above the composer, with a control that puts it back. This is a reduction the player can undo, which is the only kind allowed on this surface.

    Worst case carried: The longest prompt in the set, a 380px keyboard, and the caret mid-sentence. The submit stays in the dock, above the keyboard, and never moves.

  9. 09ASK — call & answer with artwork

    The Art Title round. The artwork is the prompt, so it leads; the instruction is the set-level one the code already resolves. A single-line input, because a title is a title.

    Worst case carried: A wide image on the narrowest phone, and the artwork sized so the input and the dock are both reachable without scrolling the image out of view.

  10. 10ASK — poll

    The state the current code cannot render. Poll and survey fall through every branch to a title-only view, so the background context a poll question carries in detail is never shown to a single player. Here it is.

    Worst case carried: Title, detail and a per-question custom instruction all present at once — the case that proves the branch is missing.

  11. 11ASK — wavelength

    Word entry. Today this is ten stacked text inputs, each with a label and an identical placeholder — 20 redundant strings and roughly 900px of form on a 375px phone. One input that commits to a chip does the same job in one screen.

    Worst case carried: Seven of ten slots used, including a long hyphenated term, so the chip wrap is real. The counter names the maximum without implying ten are required.

  12. 12Answer submitted — waiting

    REST. The dock is gone, because there is nothing to press; that absence is the design, not an omission. The receipt is the fix for the current screen's worst small habit: it clears the textarea on submit, so a player cannot see what they wrote while they wait.

    Worst case carried: A long response shown in full rather than truncated — there is a whole screen and nothing else to put on it.

  13. 13VOTE — the anonymous ballot

    The core of the redesign. One ballot, not two competing modes. Rows are numbered positionally and 1-based so a facilitator can say “look at response six” and everyone is looking at the same thing. Ranks are 44×44 buttons in the row itself, and the sticky slot bar is the answer to “what have I picked so far”.

    Worst case carried: Six responses, one of them the player's own, one of them 520 characters and clamped with a recoverable Show all. Two of three ranks already placed, so the submit is still disabled and says why.

  14. 14VOTE — twenty responses, paged

    The worst-case ballot. Pages carry absolute ranges (Responses 9–16 of 20) and the numbers never reindex, so page 2 still contains response eleven and nothing else does. The slot bar keeps picks made on other pages, which is the only reason paging is survivable at all.

    Worst case carried: Twenty responses in a room of twenty; the player is on page 2 with two ranks already placed on page 1 and page 3, and neither is on screen.

  15. 15Votes submitted — waiting

    REST again, and the receipt matters more here than after an answer: the ballot is about to be replaced by a named one, and a player who cannot remember what they picked has no way to check.

    Worst case carried: The ballot the player submitted, by absolute response number — the same handles the host will read aloud.

  16. 16RESULTS — trivia

    WATCH. The phone answers exactly one question — how did I do — because that is the one thing the host screen is forbidden to show (host spec §7.15: never name a person on the stage). The distribution, the leaderboard and the discussion stay up there.

    Worst case carried: The player got it wrong. Wrong is muted plus the word — never red, and never colour alone. The correct row carries a 2px rule and the word CORRECT.

  17. 17RESULTS — call & answer

    The reveal. This is the moment the anonymity feature pays off, so the phone says plainly which numbered response was yours — the number the room has been discussing for two minutes — and what it earned. It does not reproduce the room's leaderboard.

    Worst case carried: A middling result, not a win: two votes, third place, a rank that went down. Designed for the eleven players who did not come first.

  18. 18RESULTS — wavelength

    The cloud is the room's result and it belongs on the stage. The phone's version of the same fact is personal: which of your words the room also said. Today the phone renders a full common-words list, a stats block and your words — three views of one dataset, on the smallest screen in the building.

    Worst case carried: Seven words, three shared. A player whose words were all unique gets the same layout with a different sentence, not an empty state.

  19. 19Between rounds

    A state the current code cannot distinguish from the lobby: any phase that is not ASK, VOTE or RESULTS renders “You're in! Waiting for the game to start…”, so after round 3 the phone tells you the session has not begun.

    Worst case carried: Round 3 finished, round 4 not yet started, and the discussion is running in the room — which is exactly when the phone should be least interesting.

  20. 20The session has ended

    A designed finale, on the surface that has never had one. Today ENDED satisfies isWaitingState(), so a finished session shows “Waiting for the game to start…” behind a dismissible modal — and once dismissed, that lobby screen is where the player stays.

    Worst case carried: One player's whole session in four numbers, and an honest final line for somebody who came fifth. No download button that 404s.

  21. 21Connection lost, mid-answer

    The failure that loses work. Today the only connection affordance is a status chip whose click handler is window.location.reload() — offered to a player in the middle of typing, which is the one moment a reload is unforgivable. Here the banner reconnects itself and the reload is withheld while there is unsent text.

    Worst case carried: The banner sits above the bar and pushes nothing off screen; the composed answer is intact and says so; the dock states what will happen rather than failing silently.

  22. 22Rejoining mid-round

    The bug this whole screen exists to kill: a player who has voted and then reloads gets a completely blank page today, because the VOTE branch is guarded on answers.length > 0 and the already-voted path returns before the answers are ever fetched. A rejoin must always say what it found.

    Worst case carried: The hardest rejoin: back mid-VOTE, with a ballot already cast, and the ballot list deliberately not re-fetched — there is nothing left to do with it.

  23. 23The derivation, shown

    Not a state — the reference card. Three ladders, each derived from a viewing distance and a CSS pixel density rather than chosen, with live specimens so the numbers can be checked against something visible. Open it at 375, 768 and 1280 to see each ladder in force.

    Worst case carried: The rungs are the same angular sizes at all three distances, which is why the pixel numbers differ and the screens look the same size to the reader.

Warm Summit tokens unchanged. Type ladders derived per viewing distance in 23 and RATIONALE.md §3 — the host spec's projector ladder is deliberately not used, and neither is its black-lift contrast model. Every file is standalone HTML: no build step, no CDN, no external asset. They are regenerated by build.py so the one stylesheet cannot drift between states; view.html is hand-written and is not generated.
