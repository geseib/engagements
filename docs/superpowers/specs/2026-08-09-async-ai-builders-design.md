# Async generation for the four remaining AI builders

**Date:** 2026-08-09
**Status:** approved design, not yet implemented
**Reference implementation:** `lambda-functions/admin/ai-generate-scenarios.js` (already converted)

## Problem

`RestApi` is an `AWS::Serverless::HttpApi`. Its 30-second integration timeout is a
hard, non-configurable ceiling, while the Lambdas behind it are configured for 900s.
Generation that runs inside the HTTP request therefore races a wall clock it cannot
see, and when it loses, API Gateway returns its own non-JSON 503 while the Lambda is
still working. That is the failure already fixed for scenarios.

Four builders still generate inside the request:

| Component | Lambda | max_tokens formula |
|---|---|---|
| `TriviaAIBuilder.jsx` | `ai-generate-trivia.js` | `1000 + count * 500` |
| `PollAIBuilder.jsx` | `ai-generate-polls.js` | `800 + count * 300` |
| `SurveyAIBuilder.jsx` | `ai-generate-survey.js` | `1500 + count * 250` |
| `AIAssistant.jsx` | `ai-generate-questions.js` | `1000 + count * 700` |

They fail less often only because their per-item output is smaller. The architecture
is identical: the client fans out parallel batches via `runWithConcurrency` +
`postGenerationBatch`, and every one of those calls races the same ceiling. The
survey builder is the worst placed — it is a single un-chunked call for up to 50
questions, and its own source comments admit counts above ~10 risk the timeout.

## Findings that change the brief

Two defects were called out as likely present in all four. Neither is:

1. **Stale prompt-template key.** None of the four reads a prompt template from
   DynamoDB at all. They build prompts by inline string concatenation. `grep -rn
   'AIPROMPT#GENERATION' lambda-functions src scripts` matches only
   `ai-generate-scenarios.js` and the two migration scripts. No fix needed.

2. **`Math.min(n, 24, chunkCount)` category clamp.** None of the four has a category
   clamp, because none of them honours category configuration at all.

A different, silent defect is present instead:

3. **Trivia's category controls have never worked.** `TriviaAIBuilder.jsx:87` sends
   `numberOfCategories` and `mustHaveCategories` on every request;
   `ai-generate-trivia.js:28` does not destructure them and no line of the handler
   references them. The UI has always been inert. This is fixed during the
   conversion, clamping against the **total** rather than the chunk size — the
   correct form of the clamp the brief warned about.

4. **AI-suggested tags do not survive save.** `AdminPage.jsx:615` serializes to CSV
   with headers `Category,Question#,Title,Detail_lesson,School,CustomInstruction`,
   and `upload-questions.js` contains no tag handling whatsoever. Tags generated by
   the scenarios builder today are displayed, are editable, and are then discarded at
   upload. Persisting them is in scope (see Decisions).

## Decisions

| Decision | Choice |
|---|---|
| Survey envelope | Worker stores questions as flat `items[]`; `SurveyAIBuilder` rebuilds `{title, description, ...}` from the config it already holds. `generation-jobs.js` is untouched. The AI no longer rewrites the survey title/description — the typed values are used verbatim. |
| Tags | Generate **and persist** end-to-end. All four lambdas emit tags; the CSV contract and `upload-questions.js` gain an optional `Tags` column. This also makes tags real for the scenarios builder, where they are currently a dead end. |
| Single-question refine (`AIAssistant`, `questionIndex !== -1`) | Routed through the job like everything else. One code path; no synchronous branch left racing the ceiling. Costs one ~2s poll round trip. |

## Architecture

### Shared code

`generation-jobs.js` and `tags.js` are reused unchanged.

`structured-generation.js` gains per-kind entries in `PER_ITEM_TOKENS`
(`trivia`, `poll`, `survey`, `question`) so `itemsPerCall` / `maxTokensFor` size
chunks correctly for each. Its existing `buildItemsTool` hardcodes the scenario item
shape and fits none of the four, so **each lambda owns its own tool schema and length
guidance**, declared next to the prompt that depends on it. `invokeStructured`
already takes `tool` as a parameter and is not modified. Scenario behaviour is
therefore bit-identical after this change; `tests/scenario-generation-job.js`
(30/30 green today) is the guard.

`tagGuidance()` is shared as-is by all five builders.

### Per-lambda handler shape

Identical three-mode dispatch to `ai-generate-scenarios.js`:

- `event.__workerMode === true` → run the worker against the 900s function timeout.
- `GET` or `pathParameters.jobId` → return `jobToResponse(getJob(...))`.
- `POST` → `createJob`, self-invoke with `InvocationType: 'Event'`, return
  `202 {jobId, status, requested}`. A failed dispatch writes the reason onto the job
  row before returning 500, so a client polling a job that will never start gets an
  explanation instead of a permanent 404.

The worker loop, per chunk:

1. Budget check against `context.getRemainingTimeInMillis()`; stop cleanly and record
   a warning rather than being killed mid-call. A saved partial beats a lost whole.
2. Build the prompt with `alreadyUsedTitles` from everything produced so far.
3. `invokeStructured`; on `OutputTruncatedError` with `chunkSize > 1`, halve and retry
   once.
4. Normalize, drop near-duplicates, append.
5. `updateJobProgress` with `completed`, `phase`, `items`, `warnings` — so partial
   results are visible while the run continues and survive a mid-run death.
6. Stop early if a pass yields zero new items.

### What is deleted

The `planTopics` phase-1 round trip is removed from all four lambdas and all three
components that use it. Sequential chunks that can see prior titles are what topic
planning was approximating, at one fewer network round trip and one fewer Bedrock
call. After removal these become provably unreferenced (verified by grep across
`lambda-functions/` and `src/src/`) and are deleted:

- `aiBatchClient.js`: `planGenerationTopics`, `dropNearDuplicates`, `runWithConcurrency`
- `shared/bedrock-utils.js`: `planTopicList`, `buildTopicAssignmentText`, `invokeClaudeWithRetry`

`postGenerationBatch` and `describeHttpError` stay — `startGenerationJob` uses them.
`retryWithBackoff` stays — `structured-generation.js` uses it.

### Per-component shape

The `CHUNK_SIZE` / `MAX_PARALLEL` / `runWithConcurrency` / `dropNearDuplicates` block
collapses to `startGenerationJob` + `pollGenerationJob`, with an `onProgress` that
streams partial items into state, matching `AIScenarioBuilder.jsx:439-462`. Each
builder also gains the editable tag field `AIScenarioBuilder` already has.

### Tag persistence

- CSV generators gain a trailing `Tags` column, values joined with `|`
  (kebab-case, so no quote-escaping hazard in the existing naive `"${v}"`
  interpolation): `AdminPage.jsx` `generateScenariosCSV` / `generateTriviaCSV` /
  `generatePollCSV`, `BuilderPage.jsx` `generateCSVContent`, and
  `TriviaAIBuilder.jsx` `generateTriviaCSV`.
- `upload-questions.js` resolves a `Tags` column by the same
  `getColumnIndex` + fuzzy-fallback pattern it uses for every other column, and
  normalizes through the shared vocabulary. The column is **optional**: absent
  header ⇒ `tags: []`, so every existing CSV keeps importing unchanged.
- Surveys export as JSON, not CSV, so survey tags persist with no format change.

### Template

Each of the four functions gains:

- `GET /admin/ai-generate-<x>/{jobId}` with `CognitoAuthorizer`
- a `lambda:InvokeFunction` statement scoped to its own function ARN

All four already have `Timeout: 900`, `MemorySize: 1024`, `DynamoDBCrudPolicy` and
`TABLE_NAME`. `ACCOUNT_ID` is inherited from `Globals`. `@aws-sdk/client-lambda` is
already in `lambda-functions/admin/package.json`.

## Testing

One integration test per converted lambda, modelled on
`tests/scenario-generation-job.js`: `Module._load` stubs for
`@aws-sdk/client-bedrock-runtime`, `@aws-sdk/client-dynamodb`,
`@aws-sdk/lib-dynamodb` and `@aws-sdk/client-lambda`, driving the **real** handler.

Each asserts the structural regression and the shape-specific ones:

- POST returns 202 + `jobId`, and performs **zero** Bedrock calls — the 503 fix.
- The worker is dispatched as an `Event` invoke, not `RequestResponse`.
- A failed self-invoke marks the job `error` with a readable message.
- Progress is written incrementally; a mid-run failure keeps what was produced.
- `stop_reason: 'max_tokens'` surfaces as truncation and halves the chunk.
- Later chunks receive earlier titles in the prompt.
- Per-shape: trivia `correctAnswer` stays an `OptionX` id (and an array when
  `numCorrect > 1`); polls keep `options[]` / `allowMultiple`; survey keeps
  `type` / `scale` / `textType`; questions branch by `engagementType`, and the
  refine path forwards `existingQuestion`.
- Trivia honours `numberOfCategories`, clamped against the total, never collapsing
  to 1 for a single-item chunk.
- Tags are normalized on every item.

Plus one test for `upload-questions.js` tag parsing: a CSV **with** a `Tags` column
imports normalized tags; a CSV **without** one still imports cleanly with `tags: []`.

## Out of scope

- Deployment. The owner deploys.
- The naive CSV quoting in the existing generators (a `"` in any field breaks the
  row). Pre-existing, unrelated to this change, and the `Tags` column is
  kebab-case so it cannot make it worse.
- Wiring tag *filtering* into the question-set browse UI. This change makes tags
  persist; consuming them is a follow-up.
